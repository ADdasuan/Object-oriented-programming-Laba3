## 📌 Техническое задание (ТЗ)

### Общие требования

1. **Проект на git** – весь код в репозитории с историей изменений.
2. **Интерактивный диалоговый интерфейс** – для проверки корректности программы.
3. **Корректное завершение** – без `exit`, `abort`, `std::terminate`, без утечек памяти.
4. **Высокоуровневые подходы** – `std::copy`, `std::string`, исключения вместо кодов возврата.
5. **Логичная структура** – каждый класс в своих `.h` и `.cpp`, диалоговые функции и `main` – в отдельных файлах.
6. **Автосборка** – CMake (или qmake/Makefile).
7. **Статический анализ** – Clang Static Analyzer / SonarQube / VS Code Analysis. Все замечания исправлены или обоснованы.
8. **Динамический анализ** – Valgrind / Deleaker / Thread Sanitizer. Утечки памяти и race conditions отсутствуют.
9. **Качество кода** – SOLID, DRY, разумная декомпозиция.
10. **Стандарт языка** – C++20 или C++23.
11. **Сдача в IDE** – с настроенным LSP.

### Требования к задаче

1. **Категория варианта** – сложный (множитель баллов).
2. **Модульные тесты** – покрытие методов классов ≥50% (Google Test / Catch2).
3. **SOLID** – строгое следование принципам.
4. **Doxygen-документация** – всех публичных методов.
5. **Архитектура MVC/MVP** – разделение на Model, View, Controller/Presenter.
6. **Thread Sanitizer** – отсутствие состязаний в многопоточной программе.
7. **Язык** – C++ (допускаются Java/C# по согласованию).

## 🎯 Описание предметной области (Вариант №26: «Форум»)

### Сущности

#### Участник (базовый класс `User`)
- **уникальный логин** (`std::string`)
- **дата регистрации** (`std::chrono::system_clock::time_point`)
- **число сообщений** (`int`)
- **статус** (`enum Status: online, offline, banned`)

#### Модератор (`Moderator` – наследник `User`)
- **разумность** (`int [1..10]`)

#### Тролль (`Troll` – наследник `User`)
- **коэффициент толщины** (`float [0.1..1.0]`)
- **успешность** (`int` – число посетителей, забаненных в его присутствии)

### Хранилище
- **Шаблонный класс `OrderedTable<T>`** – упорядоченная по логину таблица пользователей.
- Реализация без использования STL-контейнеров (учебная цель).
- Поддержка итераторов (категория – bidirectional).

### Структура форума
- **Разделы (`Section`)** – имеют название и модератора.
- **Форум (`Forum`)** – содержит множество разделов.

## 🔄 Порядок выполнения работы (строго последовательно)

### 1. UML (этап проектирования)
- Диаграмма классов в нотации UML (Modelio / PlantUML / draw.io).
- Прототипы классов (header-файлы), полностью соответствующие диаграмме.

### 2. Реализация (модель – Model)
- Все классы логики (`User`, `Moderator`, `Troll`, `Section`, `Forum`).
- Проверка через тесты или простую `main`.

### 3. Шаблон (Template)
- Реализация шаблонного класса `OrderedTable<T>`.
- Методы: вставка, поиск, удаление.
- Итераторы (bidirectional) – обоснование выбора категории.
- **Запрещено** использовать STL-контейнеры внутри `OrderedTable`.

### 4. Прикладная программа (View + Controller)
Выбор одного из трёх вариантов (каждый сложнее предыдущего):
- **Вариант A (диалоговая)** – консольный ввод/вывод.
- **Вариант B (псевдографика)** – ncurses/ftxui, навигация без Enter.
- **Вариант C (графическая)** – Qt / SFML / ImGui.

### 5. Тестирование
- Unit-тесты для Model (классов логики).
- Тестирование View/Controller не требуется.

### 6. Документация
- Doxygen-документация для всех классов логики (`User`, `Moderator`, `Troll`, `Section`, `Forum`, `OrderedTable`).

### 7. Многопоточность
- Операция **«предсказание итогового результата существования каждого раздела»** выполняется параллельно.
- Каждая группа участников – в отдельном потоке.
- Примитивы синхронизации: `std::mutex`, `std::atomic`, `std::condition_variable`.
- Сравнение производительности однопоточного vs многопоточного режимов + график.
